# GitHub 项目交付
用户偏好：上传项目应包含能让非专业使用者看懂的说明，不能只上传源码。适用于完整项目及配置包；单个 Skill 的源码同步可使用已有 github-skill-backup，但项目说明仍按用户要求补齐，不把 Skill 白名单套到完整项目。

## 先准备可审阅的交付物
- 先读现有 README、上传记录与相关目录，保留已有风格，按实际缺口补文档，不每次重复整套研究。只询问会改变目标仓库、范围或可见性的关键信息。
- README 默认中文，包含：用户给定标题、一句话用途、适合谁、解决什么问题、已实现功能与限制、环境/费用前提、首次安装或启动、一个真实使用例子、目录及文档链接。
- 准备必要说明：安装/配置、日常使用、验证结果、更新记录。小项目可以集中在 README；复杂内容放 docs。目录说明与操作步骤必须匹配实际文件、命令、入口和依赖，不凑文件数，不编造截图、运行结果或已完成能力。
- 配置包明确区分“已在当前电脑配置”与“从仓库下载后还需安装”；不把配置包描述为可直接双击运行的应用。说明备份、合并和回滚，不覆盖个人模型/登录配置。
- 现有项目采用固定版本或上游代码时保留来源、许可证与署名，说明复用范围；不擅自增加或更换许可证，不因公开仓库就声称开源授权。

## 检查与上传
- 展示目标账号/仓库/可见性及新增、修改、删除清单。上传范围限定为项目与必要文档，排除登录凭据、密钥、原始个人配置、无关备份、原始会话日志、缓存和依赖目录；示例配置使用占位值。
- 只报告敏感扫描发现的位置和类型，不回显密钥；发现实际秘密则先从发布副本移除或替换，再检查，不绕过阻塞。
- 先完成本地文档与必要验证。已有明确上传授权且目标、范围清楚时继续实施；缺少授权或目标/可见性不明确时，只确认缺失部分。若同时使用的专用技能明确要求预览后确认，遵从该要求，已经覆盖同一操作的确认不重复索取。
- 核对 origin、分支和工作区，fetch 后检查是否能快进；不覆盖无关改动、不强推、不重写历史。只暂存本次明确文件，审阅 diff 并检查，再提交与推送。
- 优先现有 GitHub 连接器/CLI、浏览器登录与 Git；不为上传默认安装新插件。登录交给用户本人，不索取聊天中的密码/令牌。网络失败时核实已配置的连接方式，可为本次命令沿用现有代理，不擅自改全局代理或安全策略。
- 后续提交先更新与本次变化有关的说明和更新记录；任务不涉及的文档不机械重写。

## 交付验收
- 推送后 fetch/远端引用核对 SHA 与分支，确认预期文件和工作区状态。能查看网页时确认 README 标题和说明可见。
- 文档检查相对链接、目录、真实命令与排除项。运行测试只做改动相关检查；失败与未验证项准确记录。
- 最终给可点击仓库地址、说明入口、分支与提交号；区分已上传和只保留在本地的部分。未实际成功推送不称上传完成。
